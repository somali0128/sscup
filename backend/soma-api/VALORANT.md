# 无畏契约房间后端

`api/valorant.ts` adds a MongoDB-backed room API to the existing Soma API. Existing endpoints are unchanged.

## Production configuration

- Set `VALORANT_CREATE_PASSWORD` in the backend deployment's environment. Never put it in a `VITE_` variable or commit its value.
- Reuse existing `MONGODB_*` and `ALLOWED_ORIGINS` settings; allow the SSCup frontend origin.
- MongoDB must support transactions (Atlas replica set or a local replica set). A standalone mongod is insufficient.
- The first request creates indexes in six `valorant_*` collections. The database user needs index-creation permission.
- Run `npm run check`, deploy this backend, then deploy the frontend. No existing data migration is required.

## API contract

All requests use `Authorization: Bearer <64-hex random device token>`. Only the token SHA-256 digest is stored. Responses are private and `no-store`. Creation additionally requires the server-configured password in the POST body. Room codes never grant management privileges.

- `GET /api/valorant?code=ABC234`: role-filtered snapshot.
- `GET ...&view=games`: latest 100 accessible game summaries.
- `GET ...&view=history&gameId=<uuid>&after=<sequence>`: up to 100 history batches plus a `next` cursor.
- `POST /api/valorant`: `{ action, requestId, code?, version?, ... }`. UUID request IDs make retries idempotent. Mutations other than create/join/heartbeat require the latest room version. A stale version returns 409; refresh before a new action.
- Actions: `create` (nickname/password), `join` (nickname), `heartbeat`, `team` (left/right/null), `referee` (targetId/enabled), `settings` (unified), `start`, `spin`, `spinAll`, `nextRound`, `end`, `reset`, `transfer` (targetId), `takeover`, `remove` (targetId), `recover` (targetId/recoveryToken).
- Recovery's `recoveryToken` field is the **SHA-256 digest** generated by the new device, not its secret bearer token. Staff verify the player's identity out of band before registering the digest. Playing managers can only recover teammates. A neutral referee is required to recover opponents.

## Rules

- 13 total identities, up to five players per team. Unequal or single-sided teams may start; at least one participant is required.
- Waiting users must pick a team or be assigned referee before start. Referees cannot play. Only the host assigns referees, in the lobby.
- Start freezes roles/teams/admission, snapshots the event pool and draws once for every participant.
- Free mode allows repeated personal draws (one-second abuse cooldown). Unified mode disables all personal draws. Both modes allow managers to redraw everyone; advancing the round atomically redraws every participant.
- Host controls the lobby/start; host and referees control rounds, redraws and end. Referees can take over after 60 seconds without a host heartbeat.
- A playing host sees only their team. Non-playing managers see both teams. Identity hashes, internal state and opponent effects are never included in player snapshots/history.
- Results, room mutation and history receipt are written in a single transaction. Concurrent stale operations fail with 409 instead of overwriting a newer round or draw.
- End reveals all history to the game's members. CSV/JSON export is assembled client-side via paginated authenticated reads.
- Ended history expires exactly 30 days after end at the API boundary; MongoDB TTL removes documents asynchronously. Post-game administration does not extend final-result retention. Reset clears current results and starts a new game identity next time; old histories retain their own expiry.
- Rooms expire after 30 days without a game-changing operation (or 30 days after end). Presence is separate from room version. Device credentials persist in browser local storage; clearing browser data requires assisted recovery.

## Event edits

Edit `lib/valorant-events.ts`, keeping stable event IDs. Increase `EVENT_POOL_VERSION` on rule changes. Each game snapshots its pool at start; history stores the exact selected text. No frontend redeployment is needed for pool text changes.

## Verification

`tests/valorant.test.ts` covers capacity, role boundaries, host privacy, recovery, lock, draw modes, round behavior, takeover and reuse.

The implementation was also tested against an isolated real MongoDB replica set using the actual HTTP handler, including duplicate request receipts, atomic all-player draws, stale versions, session rotation, history visibility and expiry timestamps. Three isolated browser contexts verified phone/desktop flows, refresh recovery and CSV export. Production network latency and actual mainland-China mobile access still require a deployment smoke test.
